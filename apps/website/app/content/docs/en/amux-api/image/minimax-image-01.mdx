MiniMax Image 01 is the MiniMax image generation family, supporting **text-to-image (T2I)** and **image-to-image (I2I — character-consistency reference)**. amux-api exposes it through OpenAI-compatible image endpoints; the gateway internally converts requests into MiniMax's native `/v1/image_generation` protocol upstream and converts the response back to the OpenAI shape.

## Model Variants

| Model ID | Positioning | Status |
| --- | --- | --- |
| `MiniMax-Image-01` | General (T2I / I2I) | ✅ Available |
| `MiniMax-Image-01-live` | Stylized (manga / energetic / medieval / watercolor) | ⚠️ **Not yet supported** |

<Callout type="warn">
**`MiniMax-Image-01-live` is not yet enabled on the amux platform.** Use `MiniMax-Image-01` instead. Once Live becomes available, this doc and the pricing table will be updated accordingly.
</Callout>

See [https://api.amux.ai/pricing](https://api.amux.ai/pricing) for current pricing.

## Endpoints

amux-api exposes two OpenAI-compatible paths, both mapped to MiniMax's native [`POST /v1/image_generation`](https://platform.minimaxi.com/docs/api-reference/image-generation-t2i):

| Endpoint | Format | Use |
| --- | --- | --- |
| `POST /v1/images/generations` | `application/json` | T2I and I2I (reference image via JSON field) |
| `POST /v1/images/edits` | `multipart/form-data` | I2I (reference image as multipart file — amux auto-base64s it into `subject_reference`) |

| Field | Value |
| --- | --- |
| **Auth** | `Authorization: Bearer <AMUX_API_KEY>` |
| **Response format** | `application/json` |

### subject_reference[] (Image-to-Image — Character Reference)

MiniMax's I2I is **not generic image editing** — it's **character-consistency reference**: given the prompt and a reference image, the model preserves the subject's identity (face, hairstyle, etc.) while rendering the new scene.

<TypeTable
  type={{
    type: {
      type: 'string',
      required: true,
      description: <>Subject type. MiniMax currently only supports <code>character</code></>,
    },
    image_file: {
      type: 'string',
      required: true,
      description: <>Reference image. **String value (not array)**: a public URL or a Base64-encoded data URL (<code>data:image/jpeg;base64,...</code>). Formats: <code>JPG</code> / <code>JPEG</code> / <code>PNG</code>; per file <strong>&lt; 10 MB</strong>; for best results, upload a front-facing portrait. **Currently only 1 reference image is supported**</>,
    },
  }}
/>

Three ways to submit the reference image (pick one):

1. **JSON top-level**: `POST /v1/images/generations` with `subject_reference: [{ type, image_file }]` at the body root
2. **JSON `extra_body`** (OpenAI SDK style): `extra_body: { subject_reference: [...] }`
3. **Multipart file**: `POST /v1/images/edits` with the reference image as the `image` form field — amux reads the file → Base64 data URL → fills `subject_reference[0]` (`type` fixed to `character`)

> Compatibility: `image_file` also accepts the array form (`["data:..."]`); amux auto-flattens by taking the first non-empty element.

### style (Stylized output)

Only effective for `image-01-live` (image-01 ignores `style` upstream). **Live is not yet enabled on amux today**, so passing `style` has no real effect — included here for contract completeness.

<TypeTable
  type={{
    style_type: {
      type: 'string',
      description: <>Style type. One of <code>漫画</code> (manga) / <code>元气</code> (energetic) / <code>中世纪</code> (medieval) / <code>水彩</code> (watercolor)</>,
    },
    style_weight: {
      type: 'number',
      description: <>Style weight, range <code>(0, 1]</code>, default <code>0.8</code></>,
    },
  }}
/>

Two equivalent forms (amux normalizes both):

- **Nested object**: `style: { style_type: "...", style_weight: 0.8 }`
- **Flat**: write `style_type` / `style_weight` directly at the top level (or in `extra_body`)

### size to aspect_ratio mapping

When you set `size` without `aspect_ratio`, amux maps the OpenAI size to MiniMax's `aspect_ratio` per this table:

| `size` | `aspect_ratio` |
| --- | --- |
| `1024x1024` | `1:1` |
| `1792x1024` | `16:9` |
| `1024x1792` | `9:16` |
| `1536x1024` / `1248x832` | `3:2` |
| `1024x1536` / `832x1248` | `2:3` |
| `1152x864` | `4:3` |
| `864x1152` | `3:4` |
| `1344x576` | `21:9` |

For other `WxH` sizes, amux reduces to the lowest terms; if the reduced ratio matches one of the enum values, it's forwarded; otherwise no `aspect_ratio` is sent and MiniMax falls back to `1:1`.

### Text-to-Image — Basic

<Tabs items={['curl', 'Python', 'Node.js']}>

```bash

  -H "Authorization: Bearer $AMUX_API_KEY" \
  -H "Content-Type: application/json" \
```

### Text-to-Image — Return Base64

```bash
curl https://api.amux.ai/v1/images/generations \
  -H "Authorization: Bearer $AMUX_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "MiniMax-Image-01",
    "prompt": "A cup of hot coffee on a wooden table, top-down shot",
    "response_format": "b64_json",
    "n": 1
  }'
```

`response_format` accepts both `b64_json` (OpenAI style) and `base64` (MiniMax style); amux normalizes both to MiniMax's `base64`.

### Image-to-Image — JSON top-level subject_reference

```bash
curl https://api.amux.ai/v1/images/generations \
  -H "Authorization: Bearer $AMUX_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "MiniMax-Image-01",
    "prompt": "Close-up of a harbor worker with sunglasses, cinematic look",
    "aspect_ratio": "1:1",
    "n": 1,
    "subject_reference": [
      { "type": "character", "image_file": "https://example.com/face.jpg" }
    ]
  }'
```

Base64 data URLs are also accepted:

```json
{
  "subject_reference": [
    { "type": "character", "image_file": "data:image/jpeg;base64,/9j/4AAQSkZJRg..." }
  ]
}
```

### Image-to-Image — Multipart Upload (/v1/images/edits)

`POST /v1/images/edits` takes the reference image as the multipart `image` form field; amux reads the file → Base64 data URL → fills `subject_reference[0]` (`type` fixed to `character`). Only `MiniMax-Image-01` is accepted.

```bash
curl https://api.amux.ai/v1/images/edits \
  -H "Authorization: Bearer $AMUX_API_KEY" \
  -F "model=MiniMax-Image-01" \
  -F "prompt=Close-up of a harbor worker with sunglasses, cinematic look" \
  -F "n=1" \
  -F "size=1024x1024" \
  -F "image=@/path/to/face.jpg"
```

### Image-to-Image — OpenAI SDK via extra_body

The OpenAI SDK doesn't natively know `subject_reference`; pass it through `extra_body`:

<Tabs items={['Python', 'Node.js']}>

```python
            {"type": "character", "image_file": "https://example.com/face.jpg"}
```

## Error Response

amux maps MiniMax upstream errors into the OpenAI error shape:

```json
{
  "error": {
    "message": "...",
    "type": "minimax_image_error",
    "code": "<MiniMax base_resp.status_code>"
  }
}
```

| HTTP Status | Meaning |
| --- | --- |
| `200` | Success |
| `400` | Bad request (empty prompt, invalid `size`, missing `image` file on `/v1/images/edits`, etc.) |
| `401` | Missing or invalid API key |
| `403` | Model not authorized (e.g. using `MiniMax-Image-01-live`) or blocked by content-safety policy |
| `429` | Rate limit triggered or insufficient balance |
| `500` / `502` / `503` | Server-side error or upstream unavailable |

## FAQ

<Accordions>
  <Accordion title="Why does MiniMax-Image-01-live error out?">
    `MiniMax-Image-01-live` is **not yet enabled** on the amux platform. Use `MiniMax-Image-01` instead. Once Live is available, this doc and the pricing table will be updated.
  </Accordion>

  <Accordion title="How do I do image-to-image?">
    Pick one of three:

    1. **JSON top-level**: `POST /v1/images/generations` with `subject_reference: [{ type: "character", image_file: "..." }]`
    2. **OpenAI SDK via extra_body**: `extra_body: { subject_reference: [...] }`
    3. **Multipart**: `POST /v1/images/edits` with the image as the `image` form field — amux auto-converts

    Note: MiniMax currently supports **only 1 character reference image**, `type` is fixed to `character`, and per-file size must be `< 10 MB`.
  </Accordion>

  <Accordion title="Why don't width / height take effect?">
    The adapter forwards `model` / `prompt` / `n` / `size` / `response_format` / `watermark` / `seed` / `style` / `subject_reference` / `prompt_optimizer` / `aspect_ratio`. **Standalone `width` / `height` are not in that list** and are silently dropped today.

    Workaround: use OpenAI-style `size` (e.g. `1024x1024`, `1792x1024`) so amux maps it to `aspect_ratio` for the upstream.
  </Accordion>

  <Accordion title="What if I send both size and aspect_ratio?">
    `aspect_ratio` wins. During conversion, if `aspect_ratio` is present at the top level (or in `extra_body`), amux uses it directly; only when `aspect_ratio` is absent does it derive one from `size`.
  </Accordion>

  <Accordion title="How long are the returned URLs valid?">
    Upstream-signed image URLs expire after **24 hours** — download or persist them to your own storage promptly. To get the bytes inline, set `response_format: "b64_json"` to receive the Base64 payload in one shot.
  </Accordion>

  <Accordion title="Is image_file a string or an array?">
    MiniMax's official contract is a **string** (single value, not an array). For backwards compatibility with older blog snippets that use the array form (`["data:..."]`), amux's adapter auto-flattens by picking the first non-empty element. Prefer the string form in new code.
  </Accordion>
</Accordions>
