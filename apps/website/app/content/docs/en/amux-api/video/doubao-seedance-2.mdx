Doubao Seedance 2.0 is ByteDance Volcengine Ark's multimodal video generation model — accepts text, image, video, and audio as four input modalities, up to 9 images / 3 video segments / 3 audio segments. amux-api exposes both **Volcengine native** and **amux universal** calling paths.

<Callout type="info">
**Volcengine v3 protocol compatibility**: the Volcengine native endpoint is now fully compatible with both the **create task** and **get task status** interfaces of the Volcengine Ark v3 protocol, with request path / body aligned to Volcengine's official contract. For the full field-level format, see the dedicated docs: [Create Video Generation Task (Volcengine v3)](./volcano-create-task) and [Get Task Status (Volcengine v3)](./volcano-get-task). This page focuses on Doubao Seedance 2.0's model-specific usage.
</Callout>

## Model Variants

| Model ID | Positioning | Use Case |
| --- | --- | --- |
| `doubao-seedance-2.0` | Standard | Final renders, best quality / consistency. Supports 720p / 1080p |
| `doubao-seedance-2.0-fast` | Fast | Speed-first and cheaper — ideal for prompt iteration & rough drafts. **720p only** — does not support 1080p |

See [https://api.amux.ai/pricing](https://api.amux.ai/pricing) for current pricing.

## Create Video Generation Task

Two calling paths, sharing the same [task status endpoint](./get-task):

- **Path A (Volcengine native)**: `POST /api/v3/contents/generations/tasks` — fully compatible with the Volcengine Ark contract; Volcengine SDKs work with just a `base_url` change.
- **Path B (amux universal)**: `POST /v1/video/generations` — vendor-neutral schema; Volcengine-specific fields go through `metadata`.

### Path A — Volcengine Native Endpoint

| Field | Value |
| --- | --- |
| **Method** | `POST` |
| **Full URL** | `https://api.amux.ai/api/v3/contents/generations/tasks` |
| **Auth** | `Authorization: Bearer <AMUX_API_KEY>` |
| **Request format** | `application/json` |
| **Response format** | `application/json` |

amux's gateway treats a request as **Volcengine native format** when the body contains `content` **and** does not contain `prompt`. If both are present, the request is handled as the universal format (Path B conversion chain).

#### Scenarios & Roles

Tasks fall into 4 scenarios. **The 3 image-bearing scenarios are mutually exclusive — they cannot be mixed within a single task**:

| Scenario | image_url | video_url | audio_url |
| --- | --- | --- | --- |
| Text-to-Video | — | — | — |
| Image-to-Video (first frame) | 1, `role: first_frame` | — | — |
| Image-to-Video (first + last) | 2, `role: first_frame` + `last_frame` | — | — |
| Multimodal reference | 1–9, `role: reference_image` | 0–3 | 0–3 |

> In multimodal reference mode, all three modalities are optional — you can pass images only, videos only, audios only, or any combination.

**First/last-frame behavior**:

- The first and last frames may be the same image
- When their aspect ratios differ, **the first frame's ratio dominates** and the last frame is auto-cropped to fit

**Approximating "first/last frame + multimodal" via prompt**:

In multimodal reference mode, you can use `@imageN` in the prompt to nominate a particular reference image as a first / last frame — an indirect way to combine "first/last frame + multimodal reference". For **strict first/last-frame locking**, use the Image-to-Video (first + last) scenario with explicit `role: first_frame` / `last_frame`.

#### Resource Constraints

| Resource | Per-file limit | Duration | Count | Format |
| --- | --- | --- | --- | --- |
| Image (image_url) | 30 MB | — | See scenarios above | HTTP/HTTPS URL or Base64 data URL |
| Video (video_url) | 50 MB | [2, 15]s per segment | ≤ 3 segments, total ≤ 15s | mp4 / mov; resolutions 480p / 720p / 1080p |
| Audio (audio_url) | 15 MB | [2, 15]s per segment | ≤ 3 segments, total ≤ 15s | wav / mp3 |

<Callout type="warn">
**Overall limit**: total request body ≤ 64 MB. **Do not Base64-encode large files** — submit via public HTTP/HTTPS URLs to avoid the 64 MB cap and reduce upload latency.
</Callout>

</Callout>

#### Specifying Image Roles / Injecting Video / Audio

To attach a `role` to an image, or inject `video_url` / `audio_url` on the universal endpoint, use `metadata.content` with the full Doubao content array (same shape as Path A's [ContentItem Element](#contentitem-element)):

```json
{
  "model": "doubao-seedance-2.0",
  "prompt": "Camera pushes in slowly",
  "metadata": {
    "ratio": "16:9",
    "duration": 5,
    "content": [
      { "type": "image_url", "image_url": { "url": "https://example.com/start.jpg" }, "role": "first_frame" },
      { "type": "image_url", "image_url": { "url": "https://example.com/end.jpg"   }, "role": "last_frame"  }
    ]
  }
}
```

Images sent via top-level `image` / `images` are added to content **without a role** — the upstream applies its default. For explicit role / multimodal control, always go through `metadata.content`.

<Callout type="warn">
**3 mutually exclusive scenarios**: Image-to-Video (first frame), Image-to-Video (first + last), and Multimodal reference cannot be mixed within the same task — see [Scenarios & Roles](#scenarios--roles) above.

amux's adapter also applies one extra rule: **when content contains only `reference_image` (no first/last frame), `duration` is automatically stripped** — the upstream rejects duration in multimodal reference mode with InvalidParameter.
</Callout>

## Get Video Task Status

Regardless of whether you submitted via Path A or Path B, you can query task status and download the video through the endpoints below — pass the `id` returned at creation:

| Purpose | Endpoint |
| --- | --- |
| Query task status (universal format) | [`GET /v1/video/generations/{task_id}`](./get-task) |
| Query task status (Volcengine v3 format) | [`GET /api/v3/contents/generations/tasks/{task_id}`](./volcano-get-task) |
| Stream the video bytes | `GET /v1/videos/{task_id}/content` |

The universal format returns a normalized unified structure — see [Get Video Task Status](./get-task); the Volcengine v3 format returns the official Volcengine v3 task structure — see [Get Task Status (Volcengine v3)](./volcano-get-task).

## Pricing Notes

amux-api applies an automatic **video-input discount** for the Doubao Seedance 2.0 family: when the request content contains a `video_url` entry (continuation / multimodal video reference), the per-task price is multiplied by the upstream's "with-video-input" discount factor (~0.59 ~ 0.61). Requests without video input are billed at the base rate.

> Note: although the "with-video-input" tier has a lower per-task rate, the input video itself consumes extra input tokens. Once that's added in, the **final total cost is roughly comparable** to a request without video input — the discount is just pricing tier reclassification, not a net savings.

In addition, **`resolution: "1080p"` is priced higher than `720p`**, and `doubao-seedance-2.0-fast` does not support 1080p — see [pricing](https://api.amux.ai/pricing) for full details.

## FAQ

<Accordions>
  <Accordion title="Standard vs Fast — which one?">
    - **Quality first** → `doubao-seedance-2.0`. Better picture quality and consistency, and supports 1080p output.
    - **Speed first** → `doubao-seedance-2.0-fast`. Faster, cheaper — ideal for batch exploration / drafts. **720p only.**

    Practical workflow: iterate prompts on Fast; when satisfied, render the final clip on the standard variant (required for 1080p).
  </Accordion>

  <Accordion title="Why didn't `metadata.first_frame` take effect?">
    The Doubao adapter does not recognize `first_frame` / `last_frame` / `reference_images` as **standalone metadata keys**. They are only valid as `role` values on image_url entries inside `metadata.content`.

    Correct shape:
    ```json
    "metadata": {
      "content": [
        { "type": "image_url", "image_url": { "url": "..." }, "role": "first_frame" }
      ]
    }
    ```
  </Accordion>

  <Accordion title="Top-level `duration` not working?">
    On the universal endpoint, the Doubao adapter only reads `req.Seconds` (top-level `seconds` string field) and `metadata.duration` — **it does not read `req.Duration`**. To set duration at the top level, pass `"seconds": "5"` (string), or simply put it in `metadata.duration` (recommended).
  </Accordion>

  <Accordion title="Is `prompt` always required?">
    On the universal endpoint (Path B), yes — amux's validation layer rejects empty `prompt`, even for first/last-frame locking or pure reference-image setups (in practice, upstreams reject those too, so this is consistent with reality). On Volcengine native (Path A), supply text via the content array's `text` element.
  </Accordion>

  <Accordion title="What are the multimodal limits?">
    Per request: ≤ 9 images, ≤ 3 video segments, ≤ 3 audio segments; per-file ≤ 30 MB (image) / ≤ 50 MB (video) / ≤ 15 MB (audio); total request body ≤ 64 MB. Full rules: see [Resource Constraints](#resource-constraints) above.
  </Accordion>

  <Accordion title="My output has no audio?">
    Check `generate_audio` (default `true`). If you explicitly set it to `false`, the output is video-only. Note: some early model variants may not support audio generation — refer to the pricing table for capabilities.
  </Accordion>

  <Accordion title="I sent `trace_id` but it isn't echoed back?">
    The gateway **does not currently support** the `trace_id` and `rpf_auto_detect` upstream parameters — even if sent, they are dropped and not forwarded upstream, so callbacks will not carry `trace_id`. To correlate a callback with the original request, encode your own business identifier in the `callback_url` path or query string instead.
  </Accordion>

  <Accordion title="callback_url isn't being hit?">
    The upstream calls your `callback_url` directly from the public internet. Ensure:

    - URL is reachable from the public internet, HTTPS recommended
    - Your endpoint returns 2xx within a few seconds
    - Don't rely on callback as the only signal — combine callback + polling for safety
  </Accordion>
</Accordions>
